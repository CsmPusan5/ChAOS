## 1. Условие задачи

В вычислительный центр поступают задания, требующие определённого числа процессорных ядер, объёма памяти, времени и электрической мощности. Центр состоит из нескольких узлов с различными характеристиками. Планировщик выбирает задания из очереди и размещает их на совместимых свободных ресурсах. Суммарное энергопотребление и тепловая нагрузка ограничены. Требуется разработать консольное приложение на C, моделирующее работу центра в дискретном времени (тиками).

В работе последовательно реализованы:

1. **Многопроцессная модель** — fork-дети, обмен через POSIX shm, синхронизация неименованными POSIX-семафорами в shm.
2. **Второй механизм синхронизации** — именованные POSIX-семафоры `sem_open`/`sem_close`/`sem_unlink`, переключение флагом `-m`.
3. **Независимо запускаемые процессы** — `cluster` через `fork` + `execv`, воркер запускается вручную из другого терминала.
4. **Клиент-серверная модель** — TCP-сервер и удалённые клиенты (`node`/`task`), каждый выводит только то, что получает по сети.
5. **Множественные мониторы** — комплексный клиент `monitor`, динамическое подключение/отключение до 16 одновременно.
6. **Устойчивость к обрыву клиентов** — сервер не падает; клиент переподключается.
7. **Корректное завершение** — `SHUTDOWN` всем активным клиентам при остановке сервера.

Все режимы живут в одном бинарнике `build/sim` и переключаются подкомандой или флагом.

## 2. Сценарий отображения сущностей в процессы

Разделяемое состояние (массивы `tasks[]`, `center`, статистика, `cur_time`) — в одном блоке `SharedState` в POSIX shm. Доступ защищён `sem_mtx`. Фазы тика синхронизируются семафорами `node_sem[]`, `task_sem[]`, `sched_sem`, `ack_sem` (барьер).

### 2.1 Локальные версии (legacy / cluster)

| Сущность        | Процесс              | Функция          | Что делает                                                          |
|-----------------|----------------------|------------------|---------------------------------------------------------------------|
| Модельное время | 1 × родитель         | `run_clock`      | двигает `cur_time`, раздаёт фазы, собирает `ack`, дедлайны, энергия |
| Узел (8)        | `MAX_NODES` × воркер | `node_work`      | отказ/восстановление, роняет задачи на упавшем узле                 |
| Задание (20)    | `MAX_TASKS` × воркер | `task_work`      | поступление, проверка выполнимости, завершение                      |
| Планировщик     | 1 × воркер           | `scheduler_work` | сортировка очереди, размещение, вытеснение                          |

Итого 30 процессов. В `legacy` воркеры — форкнутые дети в том же коде; в `cluster` — отдельные запуски через `execv("/proc/self/exe", "worker", role, idx)`, обмен только через POSIX shm и именованные семафоры (env `SIM_SHM_NAME`, `SIM_SEM_PREFIX`).

### 2.2 Клиент-серверная модель

| Сущность                  | Роль               | Программа                          |
|---------------------------|--------------------|------------------------------------|
| Такты, планировщик, центр | **Сервер**         | `./sim server --port P …`          |
| Узел `i`                  | **Node-клиент**    | `./sim client --type node --idx i` |
| Задание `j`               | **Task-клиент**    | `./sim client --type task --idx j` |
| Наблюдатель               | **Monitor-клиент** | `./sim monitor --port P`           |

Каждый процесс выводит только принятое по сети. Глобального `status(t)` в клиентах нет — полную картину показывает `monitor`.

### 2.3 Один тик в локальной модели

```
ФАЗА 1 (узлы):         sem_post(node_sem[i]) × N → ack_sem × N
ФАЗА 2 (задания):      sem_post(task_sem[j]) × M → ack_sem × M
ФАЗА 3 (планировщик):  sem_post(sched_sem)       → ack_sem × 1
ПОСТ-ФАЗА (под mtx):   дедлайны, декремент time_remaining, накопление энергии
                       status(t) если verbose
```

### 2.4 Один тик в клиент-серверной модели

```
ЖИВОЙ ACCEPT (неблокирующий) — новые node/task/monitor
ФАЗА 1 (узлы):         NODE_WORK → NODE_RESULT × N (только подключённые)
ФАЗА 2 (задания):      TASK_WORK → TASK_RESULT × M (только подключённые)
ФАЗА 3 (планировщик):  scheduler_work_with_arrival(t) в сервере
ФАЗА 4 (пост):         дедлайны, декремент, энергия
РАССЫЛКА:              NODE_STATE, TASK_STATE, MONITOR_STATE
```

### 2.5 Завершение

| Событие              | Локально                       | Сервер                                   | Клиент                          |
|----------------------|--------------------------------|------------------------------------------|---------------------------------|
| `all_done` / `-t`    | `stop_flag=1`, `sem_post` всех | `SHUTDOWN` всем, `waitpid`               | получает `SHUTDOWN`, exit 0     |
| `Ctrl+C` / `SIGTERM` | `on_signal → stop_flag=1`      | `on_signal → stop_flag=1` → `SHUTDOWN`   | `on_signal_client` + `SHUTDOWN` |
| Обрыв клиента        | —                              | `close(fd)`, `fd=-1`, задачи в `WAITING` | retry 10× 1 с, `HELLO` заново   |
| Обрыв сервера        | —                              | —                                        | retry, затем `exit=1`           |

## 3. Реализация пользовательского интерфейса

Консольный интерфейс — через `write()` в `STDOUT_FILENO` и `log_fd`. В локальных версиях лог открывается с `O_TRUNC` мастером и `O_APPEND` воркерами (атомарные дописывания). В клиент-серверной — каждый процесс пишет в свой файл: `log_server.log`, `log_node_N.log`, `log_task_N.log`, `log_monitor.log`.

Формат — построчный, с меткой `[t=NNN]`:

```
[t=  3] ПОСТУПИЛО: J3 (id=2) (ядра=8 память=16ГБ мощность=180Вт ...)
[t=  3] ЗАПУЩЕНО: J3 (id=2) -> N1, N2 | режим: группа узлов
[t=  4] N1 [########............] ядра 6/16 память 12/64ГБ мощность 180/350Вт ОК
Питание: 240/1200Вт (с PUE 1.15 = 276Вт). Тепло: 240/1100Вт
Выполняются: J1(ост.3) J3(ост.6)
Ожидают: J2
```

Ключевые события: `ПОСТУПИЛО`, `ОЖИДАЕТ`, `ЗАПУЩЕНО`, `ВЫТЕСНЕНИЕ`, `ПРЕРВАНО`, `ЗАВЕРШЕНО`, `ОТКАЗ`, `ВОССТАНОВЛЕНИЕ`, `ОТКЛОНЕНО`, `ПРОСРОЧЕНО`.

Итоговая сводка `print_summary`: выполнено, отклонено, вытеснений, перезапусков, отказов узлов, суммарная энергия, средние времена ожидания и пребывания, построчная таблица по каждому заданию.

Monitor рендерит ту же картину, что `status(t)` локальных версий: ASCII-полоски загрузки ядер, питание с PUE, RUN/WAIT, накопленная статистика. Одного окна монитора достаточно для наблюдения.

## 4. Варианты запуска и завершения

### 4.1 Ключи CLI

| Ключ                      | Значение                           | По умолчанию |
|---------------------------|------------------------------------|--------------|
| `-s fcfs\|prio\|edf\|sjf` | стратегия                          | `prio`       |
| `-d N`                    | задержка между тиками, мс          | `150`        |
| `-t N`                    | период (0 — без лимита)            | `60`         |
| `-n N`                    | зерно генератора                   | `42`         |
| `-l файл`                 | файл лога                          | `log.log`    |
| `-f p`                    | вероятность отказа узла/тик        | `0.0`        |
| `-m shm\|named`           | механизм семафоров (только legacy) | `shm`        |
| `-q`                      | тихий режим                        | —            |
| `-h`                      | справка                            | —            |

### 4.2 Подкоманды

| Команда                                                    | Назначение                         |
|------------------------------------------------------------|------------------------------------|
| `./sim` (без подкоманды)                                   | legacy                             |
| `./sim -m named`                                           | именнованиые семафоры              |
| `./sim cluster`                                            | независимые процессы               |
| `./sim worker <node\|task\|sched> <idx>`                   | воркер для `cluster` (или вручную) |
| `./sim stop <pid>`                                         | `SIGTERM` мастеру                  |
| `./sim server --port P [--spawn-all]`                      | клиент-сервер                      |
| `./sim client --host H --port P --type node\|task --idx N` | клиент                             |
| `./sim monitor --host H --port P`                          | клиент-монитор                     |

### 4.3 Способы завершения

1. **Естественное** — `all_done()`.
2. **По периоду** — `t >= time_limit`.
3. **По сигналу** — `Ctrl+C` / `SIGTERM` → `stop_flag=1` → очистка → `SHUTDOWN` клиентам.
4. **По дедлайнам** — просроченные задачи → `FAILED`, очередь пустеет.
5. **Внешне** — `./sim stop <pid>`.

Во всех сценариях: `print_summary`, `close(log_fd)`, `sem_destroy` / `sem_close` + `sem_unlink`, `munmap`, `shm_unlink` (cluster), `waitpid` детей, `SHUTDOWN` клиентам.

### 6.3.1 Ручные тесты

Ниже — сценарии, которые выполняются вручную и имеют однозначный ожидаемый результат (вывод или код возврата). Каждый — независим.

**Т1. Legacy, базовая работа.**

```bash
./build/sim -s prio -t 60 -d 0 -n 42 -q
echo "exit=$?"
```

**Возвращает:** `exit=0`. В `log.log` — все 20 задач в статусе `DONE` или `FAILED`; последняя строка — `ИТОГИ`. Фазы видны: `ОТКАЗ`/`ВОССТАНОВЛЕНИЕ` идут раньше `ЗАПУЩЕНО` в пределах тика.

**Т2. Legacy, EDF и дедлайн как срок завершения.**

```bash
./build/sim -s edf -t 60 -d 0 -n 1 -q
grep -c "ПРОСРОЧЕНО" log.log
grep -c "ОТКЛОНЕНО" log.log
```

**Возвращает:** для просроченных `RUNNING`-задач — строки `ПРОСРОЧЕНО: <name> … (дедлайн N, остаток K тиков)` с `K > 0`; для `WAITING`/`PREEMPTED` — `ОТКЛОНЕНО: у <name> истёк срок`. В `ИТОГИ` сумма `Выполнено + Отклонено + Не завершено = 20`.

**Т3. Legacy, отказы узлов.**

```bash
./build/sim -f 0.05 -t 100 -d 0 -n 7 -q
grep -c "ОТКАЗ:" log.log
grep -c "ПРЕРВАНО:" log.log
grep -c "ВОССТАНОВЛЕНИЕ:" log.log
```

**Возвращает:** все три счётчика `> 0`; в `ИТОГИ` `Отказов узлов` совпадает с `grep -c "ОТКАЗ:"`.

**Т4. Именованные семафоры.**

```bash
./build/sim -m named -t 40 -d 0 -n 1 -q &
sleep 0.5
ls /dev/shm/sem.sim_* | wc -l     # пока работает
wait
ls /dev/shm/sem.sim_* 2>/dev/null | wc -l   # после
```

**Возвращает:** во время работы — `30` (mtx + 8 node + 20 task + sched + ack); после — `0`. Поведение модели идентично `-m shm` при том же seed: `diff` по логу (без шапки) пустой.

**Т5. Cluster, ручной воркер.**

```bash
./build/sim cluster -n 7 -t 100 -d 200 -q &
MASTER=$!
sleep 2
export SIM_SHM_NAME=/sim_shm_$MASTER SIM_SEM_PREFIX=/sim_$MASTER SIM_LOG_PATH=log.log
./build/sim worker node 3 &
WORKER=$!
sleep 3
kill $WORKER $MASTER
```

**Возвращает:** в `log.log` — `подключён node 3`; `pgrep -f "sim worker"` во время работы показывает 30 процессов (28 + sched + вручную подключённый — замещает один из форкнутых).

**Т6. Сервер + `--spawn-all`.**

```bash
./build/sim server --port 5555 --spawn-all -t 30 -d 100 -n 42 -q
echo "exit=$?"
grep -c "подключён node" log_server.log
grep -c "подключён task" log_server.log
grep -c "SHUTDOWN"       log_server.log
```

**Возвращает:** `exit=0`; `8`; `20`; `1` (строка `завершение — SHUTDOWN всем активным клиентам`). `pgrep -f "sim client"` после — пусто.

**Т7. Один монитор.**

```bash
./build/sim server --port 5555 --spawn-all -t 60 -d 100 -n 42 -q &
sleep 2
./build/sim monitor --host 127.0.0.1 --port 5555 -l /tmp/m.log
```

**Возвращает:** `/tmp/m.log` содержит блоки `[t=N]` с 8 узлами, строкой `Питание: … с PUE 1.15`, списками `Выполняется:` / `Ожидает:`, строкой `Итог: done=… failed=…`. Последний `[t=N]` отстаёт от финального тика сервера не более чем на 2. `exit=0` у монитора после `SHUTDOWN`.

**Т8. Множественные мониторы, kill среднего.**

```bash
./build/sim server --port 5555 --spawn-all -t 200 -d 100 -f 0.9 -n 3 -q > /dev/null 2>&1 &
sleep 2
./build/sim monitor --host 127.0.0.1 --port 5555 -l /tmp/m1.log > /dev/null 2>&1 &
./build/sim monitor --host 127.0.0.1 --port 5555 -l /tmp/m2.log > /dev/null 2>&1 &  M2=$!
./build/sim monitor --host 127.0.0.1 --port 5555 -l /tmp/m3.log > /dev/null 2>&1 &
sleep 4; kill -9 $M2; sleep 3
./build/sim monitor --host 127.0.0.1 --port 5555 -l /tmp/m4.log > /dev/null 2>&1 &
wait
grep "monitor" log_server.log
```

**Возвращает:** в `log_server.log` — `подключён monitor #0`, `#1`, `#2`, `[t=N] monitor #1 отключён (send failed)`, `[t=M] подключён monitor #1 (live)`. В `m1.log` и `m3.log` — непрерывный поток `[t=N]` без пропусков; `m4.log` начинается не с `t=0`, а с тика подключения.

**Т9. Медленный монитор (SIGSTOP).**

```bash
./build/sim server --port 5555 --spawn-all -t 200 -d 50 -f 0.9 -n 7 -q > /dev/null 2>&1 &
sleep 2
./build/sim monitor --host 127.0.0.1 --port 5555 -l /tmp/f.log > /dev/null 2>&1 &
./build/sim monitor --host 127.0.0.1 --port 5555 -l /tmp/s.log > /dev/null 2>&1 & SLOW=$!
sleep 2; kill -STOP $SLOW
sleep 10
grep "monitor .* отключён" log_server.log
kill -CONT $SLOW 2>/dev/null; kill $SLOW 2>/dev/null
```

**Возвращает:** `[t=N] monitor #1 отключён (send failed)` — через ~2–3 с после SIGSTOP. В `f.log` — непрерывный поток до финального тика. Если в вашей среде `SO_SNDTIMEO` не срабатывает за 10 с (большой TCP-буфер), используйте kill -9 (Т10).

**Т10. Убитый монитор (kill -9).**

```bash
./build/sim server --port 5555 --spawn-all -t 200 -d 50 -f 0.9 -n 7 -q > /dev/null 2>&1 &
sleep 2
./build/sim monitor --host 127.0.0.1 --port 5555 -l /tmp/f.log > /dev/null 2>&1 &
./build/sim monitor --host 127.0.0.1 --port 5555 -l /tmp/s.log > /dev/null 2>&1 & SLOW=$!
sleep 2; kill -9 $SLOW
sleep 3
grep "monitor .* отключён" log_server.log
```

**Возвращает:** `[t=N] monitor #1 отключён (send failed)` за 3 тика после `kill -9` — `poll(POLLHUP)` видит закрытый сокет мгновенно, без ожидания `EPIPE` от `write`.

**Т11. Отключение node-клиента.**

```bash
./build/sim server --port 5555 --spawn-all -t 200 -d 100 -f 0 -n 7 -q > /dev/null 2>&1 &
sleep 3
kill -9 $(pgrep -f "client.*node --idx 0")
sleep 3
grep "node 0 отвалился" log_server.log
grep "возвращён в очередь (node 0 отключён)" log_server.log | wc -l
```

**Возвращает:** `[t=N] node 0 отвалился при recv`; и ≥ 1 строка `возвращён в очередь`. Сервер продолжает работу (не падает).

**Т12. Возврат node-клиента.**

После Т11:

```bash
./build/sim client --host 127.0.0.1 --port 5555 --type node --idx 0 > /dev/null 2>&1 &
sleep 3
grep "подключён node 0" log_server.log | wc -l
```

**Возвращает:** `2` — первое в стартовом grace, второе после возврата. Задачи, ранее возвращённые в `WAITING`, снова размещаются на node 0.

**Т13. Переподключение клиента при падении сервера.**

```bash
./build/sim server --port 5555 --spawn-all -t 200 -d 100 -n 42 -q > /dev/null 2>&1 & S=$!
sleep 3
kill -9 $S
sleep 2
tail -3 log_node_0.log
```

**Возвращает:** `CLIENT node 0: обрыв, переподключение...`, затем `client: connect 127.0.0.1:5555 (1/10)...` и т.д. После 10 попыток — `сдаюсь`. `pgrep -f "sim client"` пусто (клиенты не висят зомби).

**Т14. Ctrl+C на сервере — все клиенты завершаются.**

```bash
./build/sim server --port 5555 --spawn-all -t 0 -d 100 -q > /dev/null 2>&1 & S=$!
sleep 2
kill -TERM $S
wait $S; echo "exit=$?"
sleep 0.5
pgrep -f "sim client" | wc -l
tail -1 log_node_0.log
```

**Возвращает:** `exit=0`; `0` живых клиентов; последняя строка в логе клиента — `SHUTDOWN`.

### 6.3.3 Автоматизация — `test_long.sh`

`test_long.sh` — bash-обёртка над четырьмя ключевыми сценариями (Т1-подобный прогон, Т8, Т10, слоты). Возвращает `PASS=N FAIL=M` и код `0` (все прошли) или `1` (есть провал). Время — около 70 секунд.

Покрытие:

## 7. Использование ИИ

### 7.1 Промты, использованные при работе

Промты:

**Структуры данных (основа модели).**
- "Опиши структуры `Task`, `Node`, `ComputingCenter` — поля: ядра, память, мощность (всего и занято), флаги `multi/preempt/checkpoint`, статус, карта размещения `used_mask` + массивы `alloc_cores[]`, `alloc_mem[]`, `alloc_power[]` по узлам. Объясни, зачем нужна маска `used_mask`."
  → Дало черновой `sim.h` с полями `Task`/`Node`/`ComputingCenter` и функцией `alloc_*`, работающей по маске. Позже поля расширены (флаг `checkpoint`, `arrival_time`, `deadline`).

**Генерация случайных данных.**
- "Сгенерируй случайные задания и узлы с заданными диапазонами (узлы: 2–19 ядер, 2–36 ГБ, 50–199 Вт; задания: 3–15 тиков, приоритет 1–8, вероятности `multi`/`preempt`/`checkpoint`). Вынеси в `config.c`, чтобы при одинаковом `seed` конфигурация была идентичной."
  → `create_node`, `set_center`, `create_tasks`. `srand(seed)` вызывается до генерации — воспроизводимость начальных условий гарантирована.

**Вывод статуса.**
- "Напиши `status(t)` — для каждого узла ASCII-полоска загрузки ядер (20 символов), строка питания `Σused / power_limit Вт` с расчётом через PUE, блок `Выполняются:` и `Ожидают:`. Формат строки — `[t=%3d]`, события капсом."
  → `status()` в `events.c`. Защиту от деления на ноль и сокращение длинных списков пришлось добавлять вручную.

**Многопроцессная архитектура.**
- "Спроектируй многопроцессную архитектуру: каждая сущность с поведением (`Task`, `Node`, планировщик, время) — отдельный процесс. Родитель — тактовый генератор. Синхронизация — POSIX-семафоры: `sem_mtx` защищает `tasks[]`/`center`, `node_sem[]`/`task_sem[]`/`sched_sem`/`ack_sem` — фазы тика. Обмен — POSIX shm."
  → `SharedState` в shm и общий `engine.c` с `run_clock`/`worker_process`. Барьер через `ack_sem` работает; таймаут (`sem_timedwait`) пришлось добавить вручную.

**Переход с pthread на процессы.**
- "Замени `pthread_mutex_t` на `sem_open` (или `sem_init` с `pshared=1`), `pthread_join` — на `waitpid`, глобальные массивы `tasks[]`/`center` — на `shm_open`+`mmap(MAP_SHARED)`. Добавь макросы `tasks`→`shm->tasks`, чтобы модули модели (`events.c`, `placement.c`) не менялись."
  → Переход сделан за один шаг, модели не переписаны. ИИ сначала оставил `pthread_mutex_t` в `SharedState` — пришлось убирать.

**Два режима семафоров (6 баллов).**
- "Напиши `sems_init(mode)`: при `mode=0` — `sem_init(…, pshared=1, …)` в полях `SharedState`, при `mode=1` — `sem_open("/sim_<pid>_*", …)` с `O_CREAT|O_EXCL`. Активные семафоры храни в process-local указателях `sem_mtx_p`, `node_sem_p[]`. Разрушение — `sem_destroy` или `sem_close` + `sem_unlink`."
  → `sems.c`. Переключение через флаг `-m shm|named`. ИИ не учёл, что `shm_unlink` в legacy-режиме можно делать сразу после `mmap`/`sem_open` — пришлось добавлять.

**Независимые процессы (7–8 баллов).**
- "Сделай подкоманду `cluster`: `fork` + `execv("/proc/self/exe", "worker", role, idx)`. Имена shm и префикс семафоров пробрасывай через `env` (`SIM_SHM_NAME`, `SIM_SEM_PREFIX`, `SIM_LOG_PATH`) — чтобы воркер можно было запустить вручную из другого терминала. Подкоманда `stop <pid>` — `SIGTERM` мастеру."
  → `cmd_cluster.c`. ИИ сначала не сделал обработку `fork() < 0` — добавил вручную.

**Клиент-сервер.**
- "Напиши TCP-сервер и клиентов: сервер — тактовый генератор, клиенты — узлы и задания. Протокол — построчный текстовый: `HELLO node|task <idx>`, `INIT_NODE`/`INIT_TASK`, в каждом тике `NODE_WORK` → `NODE_RESULT`, `TASK_WORK` → `TASK_RESULT`, рассылка `NODE_STATE`/`TASK_STATE`, завершение `SHUTDOWN`. IP и порт — в командной строке."
  → `net.c`, `cmd_server.c`, `cmd_client.c`. Ни сервер, ни клиенты не печатают `status(t)` — только принятые/отправленные сообщения.

**Мониторы (множественные, динамические).**
- "Сделай подкоманду `monitor` — комплексный клиент. Сервер после пост-фазы посылает `MONITOR_STATE <t>` + строки `N`/`PWR`/`RUN`/`WAIT`/`STAT` + `END`. Держи пул `fd_monitor[16]`; новый монитор занимает первый свободный слот. Установи `SO_SNDTIMEO=20 мс` на monitor-сокеты — медленный не должен блокировать остальных и тик."
  → `cmd_monitor` в `cmd_client.c`. `poll(POLLHUP) + MSG_PEEK` для детекта закрытого сокета пришлось добавить вручную — ИИ полагался только на `EPIPE` от `write`, который на TCP возвращает успех, пока данные лежат в буфере.

**Динамическое отключение клиентов.**
- "При обрыве node/task-клиента (`net_recv_line` или `net_send_line` вернул `< 0`) — `close(fd)`, `fd=-1`, без `stop_flag`. Задачи, размещённые на отключённом узле, верни в `WAITING`. При переподключении — снова `HELLO`, отправить `INIT_*` и текущий `STATE`, чтобы клиент синхронизировался."
  → `handle_connection` + `restart_tasks_on_node`. Узел нужно было пометить `NODE_FAILED` при обрыве — иначе планировщик размещал на нём задачи и они зависали — добавил вручную.

**Переподключение клиента.**
- "Клиент при обрыве должен переподключаться: 10 попыток с интервалом 1 с, затем снова `HELLO`, получить `INIT_*` и `STATE` и продолжить. При `SHUTDOWN` от сервера — выход с кодом 0."
  → `connect_with_retry`, сброс `arrival_reported` при переподключении. Флаг `arrival_reported` нужен, чтобы клиент не посылал `arrived` повторно.

**Завершение.**
- "При остановке сервера (по `-t`, `all_done`, `Ctrl+C`/`SIGTERM`) — рассылка `SHUTDOWN` всем активным клиентам (`node`, `task`, `monitor`), закрытие сокетов, `waitpid` детей при `--spawn-all`, `print_summary`, очистка shm и семафоров. Клиенты по `SHUTDOWN` завершаются с кодом 0."
  → `finish` в `cmd_server.c`. Проверено тестами Т11–Т14.

### 7.3 Что исправлено вручную

Сгруппировано по темам, чтобы было видно, где именно ошибался ИИ.

**Семантика модели**
- `try_place_multi`: память при раскладке по узлам — пропорционально ядрам + досылка остатка от целочисленного деления.
- `status`: защита от деления на ноль при `max_cores == 0`.
- `name[16]`: явный `name[len] = '\0'` (ИИ мог не поставить терминатор).
- EDF: `deadline == 0` → в конец очереди (ИИ ставил в начало).
- `cmp_jobs`: `case EDF: { … }` — блок `{}` для объявлений (иначе `-Wall` ругается).
- Дедлайн как крайний срок завершения: для `RUNNING` при просрочке — `alloc_give` + `alloc_clear`. ИИ проверял только `WAITING`/`PREEMPTED`.
- `can_ever_fit` для multi-задач: проверка наличия multi-узлов и их суммарной ёмкости (иначе задача висит в очереди до конца прогона).

**Синхронизация**
- `cur_time` под `sem_mtx` (ИИ писал без мьютекса).
- Убран лишний `sem_post(ack_sem)` при `stop_flag` — родитель уже не ждёт квитанцию.
- `wait_ack_or_stop`: `sem_timedwait` с шагом 100 мс + 5-секундный guard. ИИ ждал вечно — при пропавшем воркере это дедлок.
- `scheduler_work_with_arrival`: обёртка над `scheduler_work` — фильтр `arrival_time <= t`. Сначала через `(TaskStatus)99` (формальный UB), потом через `DONE` + массив `hidden[]`.

**Ресурсы и файлы**
- Уникальные имена shm и семафоров: `/sim_shm_<pid>` и `/sim_<pid>_*`. ИИ использовал константу — параллельные запуски сталкивались.
- `O_APPEND` у воркеров, `O_TRUNC` только у мастера — иначе воркер затирал лог мастера при старте.

**Процессы и сигналы**
- Bounds-check `idx` в `cmd_worker` — при `worker node 100` был бы OOB.
- Обработчики `SIGINT`/`SIGTERM` + `signal(SIGPIPE, SIG_IGN)` в `cmd_server` и `cmd_client`. Без этого `Ctrl+C` давал `exit=130` без сводки, а обрыв клиента убивал сервер по SIGPIPE.
- `stop_flag` в стартовом `accept`-цикле — иначе `Ctrl+C` не выходил из ожидания клиентов.
- `fork() < 0` при `spawn_all` → `expected--`, иначе `accept` висит вечно в ожидании клиента, которого не будет.

**Клиент-сервер: устойчивость**
- Узел при обрыве: `NODE_FAILED`, при переподключении — `NODE_OK`. Иначе задачи размещались на недоступном узле и "зависали" в `RUNNING`.
- `SO_SNDTIMEO = 20 мс` на node/task/monitor — медленный клиент не задерживает тик.
- `socket_alive` через `poll(POLLHUP) + MSG_PEEK` перед `monitor_send_state`. ИИ полагался только на `EPIPE` от `write` — но `write` возвращает успех, пока данные лежат в `SO_SNDBUF`; `EPIPE` появляется только при переполнении буфера, что может не наступить за разумное время.
- `mon_strikes[16]` — 3 подряд неудачи перед отключением монитора. Единичный всплеск нагрузки не должен убивать живой монитор.

**Тестовая инфраструктура**
- `> /dev/null` у мониторов в `test_long.sh` — 20 параллельных мониторов не делят один tty, иначе `write(STDOUT)` блокируется и сервер отключает их до регистрации.

### 7.4 Критическая оценка

ИИ хорошо справляется с механической и объёмной частью: шаблоны структур, форматирование вывода, `Makefile`, каркас фаз, рутинный переход с pthread на sem/shm, TCP-обёртки, типовой producer-consumer. Он корректно воспроизводит паттерн "семафоры + критическая секция" и правильно расставляет `sem_post`/`sem_wait`.

ИИ плохо справляется с:

- **семантикой предметной области** — приоритеты, дедлайн как срок завершения, откаты при распределении, различие "нет значения" и "нулевое значение";
- **тонкостями синхронизации** — `cur_time` без мьютекса, лишний `sem_post`, `wait_ack` без таймаута, воркер висит после аварии — всё это ловится только чтением кода или `tsan`;
- **переходом на процессы** — ИИ сначала оставил `pthread_mutex_t` в `SharedState`, не учёл наследование именованных семафоров через `fork`/`exec`, разницу "имя можно `unlink` сразу" vs "только после `waitpid`";
- **клиент-серверной моделью** — не фильтрует `arrival_time`, не ставит обработчики сигналов, не обрабатывает `fork() < 0`, забывает `SO_SNDTIMEO`, не помечает узел `NODE_FAILED` при обрыве;
- **поведением `write()` в TCP** — ИИ не учитывает, что `write` возвращает успех, даже когда удалённый сокет закрыт (данные лежат в `SO_SNDBUF`); `EPIPE` появляется только при переполнении буфера. Правильный детект — `poll(POLLHUP) + MSG_PEEK`, что пришлось добавлять вручную;
- **пограничными случаями** — `idx` без bounds-check, multi без multi-узлов, `deadline == 0` в конце очереди, остатки от деления в `try_place_multi`.

**Вывод:** ИИ ускоряет каркас и рутину, но проектирование архитектуры, выбор механизма синхронизации под каждую подзадачу и проверку корректности нужно делать вручную.

## 8. Дополнительные решения

- **Три уровня локальной модели + клиент-сервер в одном бинаре** — регрессий нет.
- **Единый `SharedState`** в POSIX shm; модули модели **не знают** о переходе с потоков на процессы (макросы `tasks`, `center`, …).
- **`sems_init`/`sems_destroy`/`sems_attach_named`** — единственное место, где различаются режимы синхронизации.
- **Барьер `ack_sem`** через `sem_timedwait` — не блокирует при `Ctrl+C`, защищает от дедлока.
- **`fork+execv("/proc/self/exe")`** — воркер запускается вручную из другого терминала.
- **Уникальные имена shm/семафоров** через PID.
- **Динамическое отключение клиентов**: сервер не падает, задачи на узле → `WAITING`, `time_remaining--` только для RUNNING с активным клиентом.
- **Переподключение**: retry 10× 1 с; `INIT_*` + `STATE`; `arrival_reported` сбрасывается.
- **Множественные мониторы**: пул 16 слотов, `SO_SNDTIMEO` 20 мс + `poll`, `mon_strikes` 3 подряд.
- **Корректное завершение**: `SHUTDOWN` всем, `waitpid`, очистка shm и семафоров.
- **Воспроизводимость**: `srand(seed)` до `init_simulation()`, дети пересеиваются независимо.
- **Интеграционные тесты `test_long.sh`** — 10 проверок (динамика мониторов, изоляция медленного, переполнение слотов, длинный прогон).

## 9. Выводы

Программа моделирует работу вычислительного центра как систему из 30 асинхронных процессов (родитель + 8 узлов + 20 заданий + планировщик) в локальных версиях, и как клиент-серверное TCP-приложение с удалёнными клиентами и мониторами в распределённой.

Все уровни требований выполнены:

- **Многопроцессная модель**: POSIX shm, неименованные семафоры в shm, корректное завершение по любому из сценариев.
- **Именованные POSIX-семафоры**: второй механизм, переключение флагом `-m`, поведение идентично.
- **Независимо запускаемые процессы**: через `fork+execv`, обмен только через именованные семафоры и shm, воркер запускается вручную.
- **Клиент-сервер**: TCP, каждый процесс выводит только принятое; сервер не выводит `status(t)`.
- **Monitor**: отдельный клиент с полной картиной модели, подключается в любой момент.
  - **Множественные мониторы**: до 16, динамическое подключение/отключение, медленные изолируются через `poll` + `SO_SNDTIMEO`.
- **Динамическое отключение клиентов**: сервер продолжает работу, задачи на отключённом узле переразмещаются при возврате.
- **Корректное завершение**: `SHUTDOWN` всем активным при остановке сервера.

Все инварианты соблюдены: занятые ресурсы ≤ доступных, `Σused·PUE ≤ power_limit`, `Σused ≤ cooling_limit`, при завершении/вытеснении/просрочке ресурсы освобождаются. Программа собирается без предупреждений с `-Wall -Wextra -pthread -lrt`; интеграционные тесты `test_long.sh` — `PASS=10 FAIL=0`; лог сохраняется в файл; все режимы сосуществуют в одном бинаре без регрессий.
