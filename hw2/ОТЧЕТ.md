## 1. Условие задачи

В вычислительный центр поступают задания, требующие определённого числа процессорных ядер, объёма памяти, времени и электрической мощности. Центр состоит из нескольких узлов с различными характеристиками. Планировщик выбирает задания из очереди и размещает их на совместимых свободных ресурсах. Суммарное энергопотребление и тепловая нагрузка ограничены. Требуется разработать консольное многопоточное приложение на C (pthread, семафоры, мьютексы), моделирующее работу центра в дискретном времени (тиками).

## 2. Сценарий отображения сущностей в потоки

В модели выделены все сущности, обладающие поведением; каждая такая сущность представлена отдельным pthread-потоком.

| Предметная область | Поток | Функция | Что делает |
|---|---|---|---|
| Модельное время (тик) | 1 × `clock_thread` | `clock_thread` | двигает `cur_time`, раздаёт фазы, собирает квитанции, публикует статус, обрабатывает прерывание |
| Вычислительный узел | `MAX_NODES` (8) × `worker_thread` | `node_work` | проверяет отказ, ведёт восстановление, при отказе «роняет» размещённые на нём задания |
| Задание | `MAX_TASKS` (20) × `worker_thread` | `task_work` | поступление в модель, проверка выполнимости, завершение по исчерпанию `time_remaining` |
| Планировщик | 1 × `worker_thread` | `scheduler_work` | сортирует очередь по стратегии, раздаёт ресурсы, при нехватке — вытеснение |
| Диспетчер ресурсов | (разделяемый код) | `placement.c` | single/multi/preempt; вызывается из `scheduler_work` |
| Учёт питания и охлаждения | (разделяемый код) | `resources.c` | `power_ok`, `alloc_take/give/clear` |
| Генератор конфигурации | (однократно) | `config.c` | создаёт узлы и задания до старта потоков |

Итого: 30 потоков (включая `main`).

Аргумент рабочего потока — `WorkerArg { int type; int index; }`:
`type = 1` — узел, `2` — задание, `3` — планировщик; `index` — номер в соответствующем массиве.

### Синхронизация

| Примитив | Назначение |
|---|---|
| `pthread_mutex_t mtx` | защита **всего** разделяемого состояния: `tasks[]`, `center.nodes[]`, счётчиков статистики, `cur_time` |
| `sem_t node_sem[MAX_NODES]` | будит поток узла `i` к очередной фазе |
| `sem_t task_sem[MAX_TASKS]` | будит поток задания `i` к очередной фазе |
| `sem_t sched_sem` | будит поток планировщика |
| `sem_t ack_sem` | квитанция «фаза выполнена»; `clock_thread` ждёт **N+M+1** таких сигналов — это аналог barrier |

Мьютекс обеспечивает взаимное исключение, семафоры — асинхронное взаимодействие между `clock_thread` и рабочими потоками.

### Один тик

`clock_thread` последовательно проигрывает три фазы, между которыми ждёт квитанции от всех рабочих:

```
ФАЗА 1 (узлы):         sem_post × N  →  ack_sem × N
ФАЗА 2 (задания):      sem_post × M  →  ack_sem × M
ФАЗА 3 (планировщик):  sem_post × 1  →  ack_sem × 1
ПОСТ-ФАЗА:             под mtx — дедлайны, декремент, накопление энергии
                       status(t) (если verbose), delay_ms
```

Внутри каждой фазы рабочие потоки выполняются параллельно. Порядок между потоками одной фазы определяется планировщиком ОС и недетерминирован.

### Завершение

`clock_thread` заканчивает свою работу по любому из условий (`stop_flag`, `-t`, `all_done()`), затем:

```c
stop_flag = 1;
sem_post(&node_sem[i]) для всех i;
sem_post(&task_sem[i]) для всех i;
sem_post(&sched_sem);
```

Рабочие просыпаются, видят флаг, выходят из циклов. `main` делает `pthread_join` по всем 30 потокам, затем `print_summary`, `close(log_fd)`, `sem_destroy`/`pthread_mutex_destroy`.

## 3. Реализация пользовательского интерфейса

Консольный интерфейс — через системные вызовы `write()` по дескрипторам `STDOUT_FILENO` и `log_fd`. Все сообщения дублируются в `stdout` и файл протокола.

Формат — построчный, каждый тик начинается с метки `[t=NNN]`:

```text
[t= 3] ПОСТУПИЛО: J3 (id=2) (ядра=8 память=16ГБ мощность=180Вт ...)
[t= 3] ЗАПУЩЕНО: J3 (id=2) -> N1, N2 | режим: группа узлов
[t= 4] N1 [########............] ядра 6/16 память 12/64ГБ мощность 180/350Вт ОК
Питание: 240/1200Вт (с PUE 1.15 = 276Вт). Тепло: 240/1100Вт
Выполняются: J1(ост.3) J3(ост.6)
Ожидают: J2
```

Ключевые события: `ПОСТУПИЛО`, `ОЖИДАЕТ`, `ЗАПУЩЕНО`, `ВЫТЕСНЕНИЕ`, `ПРЕРВАНО`, `ЗАВЕРШЕНО`, `ОТКАЗ`, `ВОССТАНОВЛЕНИЕ`, `ОТКЛОНЕНО`. В конце печатается расширенная сводка: сколько выполнено, отклонено, сколько было вытеснений, перезапусков, отказов, суммарная энергия, средние времена ожидания и пребывания, построчная таблица по каждому заданию.

Вывод статуса выполняется из `clock_thread` после того, как все три фазы отработали — то есть наблюдатель видит консистентное состояние (никто не пишет в `tasks[]`/`center.nodes[]` в этот момент).

Задержка между тиками (`-d`) обеспечивает наглядность.

## 4. Варианты запуска и завершения

**Запуск** (`main.c`, разбор `argv`):

| Ключ | Назначение |
|---|---|
| `-s fcfs\|prio\|edf\|sjf` | стратегия планирования |
| `-d N` | задержка между тиками, мс |
| `-t N` | период наблюдения (0 — без ограничения) |
| `-n N` | зерно генератора |
| `-l файл` | файл протокола |
| `-f p` | вероятность отказа узла за тик |
| `-q` | тихий режим (без статуса каждый тик) |
| `-h` | справка |

**Варианты завершения:**

1. **Естественное** — все задания достигли `DONE` или `FAILED` (проверяется `all_done()` в `clock_thread`).
2. **По периоду наблюдения** — `t` достиг `time_limit`.
3. **По прерыванию** — `Ctrl+C` / `SIGTERM`; обработчик `on_signal` устанавливает `stop_flag = 1`, `clock_thread` завершает текущий тик, будит всех рабочих через `sem_post`, программа завершается через `pthread_join`.
4. **По истечении дедлайнов** — задания с просроченным сроком переводятся в `FAILED` в пост-фазе тика, очередь естественно пустеет.

Во всех вариантах вызывается `print_summary()`, поток `log_fd` закрывается через `close()`, семафоры уничтожаются через `sem_destroy()`.

## 6. Результаты работы

**Тест 1.** `./build/sim -s prio -t 60`
Задания обслуживаются по приоритету; J3 (приоритет 1) вытесняет J1 (приоритет 2); в логе видны все ключевые события. Фазы узлов/заданий/планировщика видны по тому, что сообщения `ВОССТАНОВЛЕНИЕ`/`ОТКАЗ` всегда идут раньше `ЗАПУЩЕНО` в пределах одного тика.

**Тест 2.** `./build/sim -s edf -t 60`
Задания с дедлайном запускаются раньше; задания с `deadline = 0` уходят в конец очереди; просроченные переводятся в `FAILED` в пост-фазе (после `scheduler_work`, до `advance()` — как и в однопоточной модели).

**Тест 3.** `./build/sim -f 0.05 -t 100`
При вероятности 5% в логе появляются `ОТКАЗ`, `ПРЕРВАНО`, `ВОССТАНОВЛЕНИЕ`. Отказ обрабатывается в **фазе узлов** — до планирования того же тика, — поэтому прерванное задание успевает вернуться в очередь и быть переразмещённым **в этом же тике**.

**Тест 4.** `./build/sim -q -d 0`
Программа работает без визуальных задержек, статус не печатается, итоги корректны. За 100 тиков все задания либо `DONE`, либо `FAILED`.

**Тест 5.** `Ctrl+C` во время работы (`timeout -s INT 3 …`).
Лог содержит `ПРЕРВАНО ПОЛЬЗОВАТЕЛЕМ` и полную сводку, exit code = 0. Все 30 потоков завершаются через `pthread_join`, семафоры и мьютекс уничтожаются.

**Тест 6.** `-t 0` (без лимита тиков).
Программа завершается по `all_done()` — как только все задания обработаны.

**Тест 7.** Проверка гонок (`gcc -fsanitize=thread …`).
Прогон `-t 20 -d 0 -n 42` под ThreadSanitizer не выдаёт предупреждений: все обращения к `tasks[]`, `center.nodes[]`, `cur_time` происходят под `mtx` или через happens-before семафоров.

Инварианты соблюдены во всех тестах: занятые ресурсы не превышают доступные, `Σused·PUE ≤ power_limit` и `Σused ≤ cooling_limit`, при завершении и вытеснении ресурсы освобождаются, результат задания регистрируется один раз.

## 7. Использование ИИ

### Промты, использованные при работе

- Напиши на C структуры Task и Node: ядра, память, мощность, флаги multi/preempt/checkpoint, состояние, карта размещения.

- Напиши шаблон генерации случайных заданий и узлов.

- Напиши функцию вывода статуса узла с ASCII-полоской загрузки ядер длиной 20 символов.

- Добавь к статусу строку про питание с учётом PUE и охлаждения, блоки «Выполняются»/«Ожидают».

- Оформи лог: [t=%3d], события капсом, рамка =.

- Напиши итоговую сводку: общая статистика + таблица по заданиям.

- Составь Makefile с src/, build/, wildcard/patsubst, -std=c11 -Wall -Wextra -O2.

- Спроектируй многопоточную архитектуру: каждая сущность с поведением — отдельный pthread, clock_thread раздаёт фазы, рабочие синхронизируются семафорами, общее состояние — под мьютексом.

- Набор примитивов: mtx, node_sem[], task_sem[], sched_sem, ack_sem (барьер между фазами).

- Напиши worker_thread и clock_thread с тремя фазами и ack_sem.

- Разложи arrivals/do_repairs/completion/schedule/check_deadlines/do_failures/advance на node_work/task_work/scheduler_work + пост-фаза в часах.

- on_signal через volatile sig_atomic_t, delay_ms через nanosleep.

### Что сгенерировано ИИ

- Черновые Task/Node, заготовки create_tasks/create_node.

- status() с ASCII-полоской, оформление лога, print_summary.

- Шаблон Makefile с wildcard/patsubst.

- WorkerArg, extern-объявления примитивов.

- Каркасы clock_thread и worker_thread - только скелет цикла, без пост-фазы и краевых случаев.

- Заготовки node_work/task_work/scheduler_work.

### Что исправлено вручную

- try_place_multi: память — пропорционально ядрам + досылка остатка (ИИ терял остатки от целочисленного деления).

- status: защита от деления на ноль при max_cores == 0.

- name[16]: явный name[len] = '\0' (ИИ мог оставить без терминатора).

- EDF: deadline == 0 -> в конец очереди (ИИ ставил в начало).

- Убран лишний sem_post(&ack_sem) при stop_flag - постил квитанцию, когда часы уже не ждут.

- free(WorkerArg) в worker_thread - ИИ не освобождал malloc из main.

- case EDF: { … } в cmp_jobs - ИИ оставил объявления в case без блока {}.

- Порядок фаз «узлы → задания → планировщик» и пост-фаза - ИИ предлагал оставить старый порядок; переделано, зафиксировано комментарием в node_work.

### Критическая оценка

ИИ хорошо справляется с механическими и объёмными частями: шаблоны структур, форматирование вывода, служебные функции, Makefile, каркас потоковых циклов. Он корректно воспроизводит паттерн «producer-consumer через семафоры + мьютекс на критическую секцию» и правильно расставляет `sem_post`/`sem_wait`.

ИИ плохо справляется с:
- **семантикой предметной области** (тонкости приоритетов, откатов в транзакциях распределения ресурсов, различия «нет значения» vs «нулевое значение»);
- **тонкостями синхронизации**: в первом варианте `cur_time` писался без `mtx`; при выходе делался лишний `sem_post(&ack_sem)`; `WorkerArg` не освобождался. Всё это ловится либо tsan, либо чтением кода — ИИ сам эти проблемы не видит;
- **пограничными случаями** в фазах: порядок «узлы → задания → планировщик» пришлось сознательно выбрать и обосновать, ИИ такой выбор не делал.

Вывод: ИИ ускоряет написание каркаса и рутины, но **проектирование многопоточной архитектуры и проверку корректности синхронизации** надо делать вручную.

## 8. Дополнительные решения

- **Полная модель потоков**: `clock_thread` + `MAX_NODES` узлов + `MAX_TASKS` заданий + 1 планировщик = 30 потоков, как требует задание.
- **Разделение на модули** (`output/resources/placement/events/config`) — каждый модуль отвечает за один аспект.
- **Барьер на `ack_sem`**: каждая фаза строго дожидается завершения всеми рабочими, прежде чем `clock_thread` перейдёт к следующей. Это гарантирует консистентность фаз без сложного `pthread_barrier_t`.
- **Единый механизм карты ресурсов** (`used_mask + alloc_cores/mem/power[]`) — одинаково работает и для одного узла, и для группы.
- **Обработка `SIGINT/SIGTERM`** через `volatile sig_atomic_t stop_flag` — безопасно из signal-handler'а; корректное завершение с сохранением лога.
- **Стратегии планирования** — одним компаратором; добавление новой стратегии требует 5 строк кода.
- **Воспроизводимость начальной конфигурации** через `-n seed`: `srand(seed)` вызывается **до** создания потоков, поэтому узлы и задания при одинаковом `-n` создаются одинаково.

## 9. Выводы

Программа моделирует работу вычислительного центра как систему из 30 асинхронных потоков: часы управляют фазами, узлы обрабатывают отказы и восстановления, задания — поступления и завершения, планировщик — размещение и вытеснение. Взаимодействие построено на мьютексе и семафорах, с барьером через `ack_sem` на каждой фазе. Все инварианты соблюдены, вывод информативен, программа завершается корректно по любому из сценариев (естественное, по `-t`, по `Ctrl+C`, по `all_done`), лог сохраняется в файл. Проект разбит на модули, собирается без предупреждений с `-Wall -Wextra -pthread`.
