# README - Модель вычислительного центра (вариант 45)

## Описание

Дискретная имитационная модель вычислительного центра на C. **Многопроцессная архитектура**: каждая моделируемая сущность с поведением - отдельный процесс; модельное время идёт тиками, которые синхронизируют фазы через POSIX-семафоры. Обмен данными между процессами - через разделяемую память POSIX (`shm_open` + `mmap(MAP_SHARED)`).

Программа поддерживает три уровня в одном:

| Уровень | Как запустить | Модель                                                                     | Синхронизация                                                  |
|---------|---------------|----------------------------------------------------------------------------|----------------------------------------------------------------|
| **4–5 баллов** | `./build/sim [опции]` | fork-дети (без `exec`)                                                     | `-m shm` - неименованные POSIX-семафоры в shm *(по умолчанию)* |
| **6 баллов** | `./build/sim -m named [опции]` | fork-дети (без `exec`)                                                     | `-m named` - именованные POSIX-семафоры `sem_open`             |
| **7–8 баллов** | `./build/sim cluster [опции]` | fork + `execv` - независимо запускаемые процессы, могут стартовать вручную | именованные POSIX-семафоры                                     |

Во всех режимах обмен данными - разделяемая память POSIX; логика модели (тики, фазы, планирование, размещение, отказы, дедлайны) одна и та же.

## Файлы

| Файл | Назначение                                                                                                                                                           |
|------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `sim.h` | типы `Task`, `Node`, `ComputingCenter`, `SharedState`, `WorkerArg`, макросы (`tasks` → `shm->tasks` и т.п.), прототипы                                               |
| `main.c` | глобалы, CLI, диспетчер подкоманд, `sems_init`/`sems_destroy`/`sems_attach_named`, `run_clock`, `worker_process`, `cmd_legacy`/`cmd_cluster`/`cmd_worker`/`cmd_stop` |
| `output.c` | вывод в stdout + лог (`O_APPEND` - атомарно между процессами), `delay_ms`, обработчик сигналов                                                                       |
| `resources.c` | питание, `alloc_take/give/clear`, `power_ok` (с PUE и лимитом охлаждения)                                                                                            |
| `placement.c` | размещение на узле/группе, вытеснение                                                                                                                                |
| `events.c` | фазовая работа (`node_work`, `task_work`, `scheduler_work`), `can_ever_fit`, статус, итоги                                                                           |
| `config.c` | генерация узлов и заданий                                                                                                                                            |


## Сущности

- **Node** - узел: ядра/память/мощность (всего и занято), статус `OK/FAILED`, флаг `multi`.
- **Task** - задание: требования, приоритет, дедлайн, флаги `multi/preempt/checkpoint`, состояние, карта размещения (`used_mask` + `alloc_*`).
- **ComputingCenter** - узлы + лимиты `power_limit`, `cooling_limit`, `pue`.
- **SharedState** - единый блок разделяемой памяти: `tasks[]`, `center`, все параметры запуска, статистика, `cur_time`, `stop_flag`, встроенные семафоры для `-m shm`.

## Модель процессов

| Процесс | Сколько | Роль                                                               | Что ждёт |
|---------|---------|--------------------------------------------------------------------|----------|
| `main` (родитель) | 1 | тактовый генератор (`run_clock`): двигает `cur_time`, раздаёт фазы | `sem_wait(ack_sem)` × (N+M+1) |
| узел | `MAX_NODES` (8) | `node_work` - отказ/восстановление                                 | `sem_wait(node_sem[i])` |
| задание | `MAX_TASKS` (20) | `task_work` - поступление/завершение                               | `sem_wait(task_sem[i])` |
| планировщик | 1 | `scheduler_work` - сортировка + раздача ресурсов                   | `sem_wait(sched_sem)` |

Аргумент работы - `WorkerArg { int type; int index; }`:
`type = 1` - узел, `2` - задание, `3` - планировщик.

**Различия по версиям:**

- **legacy (4–5/6 баллов)** - родитель вызывает `fork()`, дети остаются в том же адресном пространстве кода (без `exec`) и вызывают `worker_process()` в цикле; RNG пересеивается после `fork` (`srand(seed + 100000 + i)` и т.п.).
- **cluster (7–8 баллов)** - родитель делает `fork()` + `execv("/proc/self/exe", "worker", role, idx)`: каждый воркер - отдельный запуск той же программы с подкомандой `worker`. Связь исключительно через `shm_open` + `sem_open` по именам, переданным через env (`SIM_SHM_NAME`, `SIM_SEM_PREFIX`, `SIM_LOG_PATH`). Позволяет вручную запустить дополнительный воркер в другом терминале.

## Синхропримитивы

| Примитив | Тип | Назначение                                                                                              |
|----------|-----|---------------------------------------------------------------------------------------------------------|
| `sem_mtx` | `sem_t *` | Защита **всего** разделяемого состояния (`tasks[]`, `center.nodes[]`, счётчиков статистики, `cur_time`) |
| `node_sem[MAX_NODES]` | `sem_t *[]` | Будит узел `i` к очередной фазе                                                                         |
| `task_sem[MAX_TASKS]` | `sem_t *[]` | Будит задание `i` к очередной фазе                                                                      |
| `sched_sem` | `sem_t *` | Будит планировщик                                                                                       |
| `ack_sem` | `sem_t *` | Квитанция «фаза выполнена» - родитель ждёт N+M+1 раз через `sem_timedwait` (реакция на `Ctrl+C`)        |

Реализация `sem_mtx`/`node_sem`/… зависит от режима:

- `-m shm` (4–5): неименованные семафоры, `sem_init(..., pshared=1, ...)` прямо в полях `SharedState` (`sem_mtx_emb` и т.д.);
- `-m named` / `cluster` (6 / 7–8): именованные POSIX-семафоры `sem_open("/sim_<pid>_*", ...)`, `sem_close` + `sem_unlink` в конце.

Все обращения идут через макросы `sem_mtx`/`node_sem`/… => `sem_mtx_p`/`node_sem_p[]` - process-local глобалы, одинаковые в обоих режимах.

## Тик (`run_clock`)

Один тик = три последовательные фазы + пост-обработка; родитель синхронизирует фазы через `ack_sem`:

```
1. ФАЗА УЗЛОВ         => node_work для каждого узла     (отказ / восстановление)
2. ФАЗА ЗАДАНИЙ       => task_work для каждого задания  (поступление / завершение)
3. ФАЗА ПЛАНИРОВЩИКА  => scheduler_work                 (сортировка + размещение + вытеснение)
4. ПОСТ-ФАЗА          => дедлайны (снятие незавершённых), декремент времени,
                        stat_energy += total_power()
5. status(t) (если verbose) + delay_ms(tick_delay_ms)
```

### Выход

- `Ctrl+C` / `SIGTERM` → `on_signal` ставит `stop_flag = 1`; `run_clock` реагирует на это в `wait_ack_or_stop` (таймаут 100 мс) и возвращается; затем `finish:` будит всех детей, `waitpid`-ит и удаляет ресурсы;
- `-t <N>` - по достижении лимита тиков (`-t 0` - без лимита);
- `all_done()` - все задания `DONE` или `FAILED`;
- `./build/sim stop <master_pid>` - внешняя остановка мастера из другого терминала.

## Планирование (`-s`)

`cmp_jobs` сортирует очередь:

- **FCFS** - по `arrival_time`, затем по индексу;
- **PRIO** - по приоритету (1 - высший), затем по поступлению;
- **EDF** - по дедлайну, `0` (нет дедлайна) => в конец, затем по приоритету;
- **SJF** - по длительности, затем по приоритету.

## Размещение (`placement.c`)

- **single** - ищет узел, где свободно ≥ ядер/памяти/мощности запроса.
- **multi** - раскладывает ядра по нескольким `multi`-узлам (сначала самые свободные), память и мощность - пропорционально.
- **preempt** - снимает менее приоритетные `preempt`-задачи и пробует снова; жертва => `PREEMPTED` (с `checkpoint` прогресс сохраняется; без - перезапуск с `time_remaining = duration`).

`can_ever_fit` отсекает задачи уже на тике поступления, если они не поместятся в принципе:

- одиночная - нет ни одного узла с достаточной ёмкостью;
- `multi` - нет ни одного `multi`-узла, или суммарная ёмкость `multi`-узлов меньше запроса.

Проверки питания: `power_ok(add)` требует `(Σused + add)·pue ≤ power_limit` **и** `Σused + add ≤ cooling_limit`.

## Ресурсы (`resources.c`)

Операции по маске `used_mask`: `alloc_take` (занять), `alloc_give` (вернуть), `alloc_clear` (сбросить карту задачи). Все три - под `sem_mtx`.

## Генерация (`config.c`)

- **Узлы** (8): ядер `2..19`, память `2..36` ГБ (чётная), мощность `50..199` Вт, `multi` с вероятностью 75%.
- **Лимиты**: `power_limit = 0.80 · Σmax_power`, `cooling_limit = 0.75 · Σmax_power`, `pue = 1.15`.
- **Задания** (20): длительность `3..15` тиков, приоритет `1..8`, дедлайн с вероятностью 2/3, `multi` - 33%, вытесняемые - 80%, с чекпоинтом - 67%.

## Инварианты

- занятые ресурсы ≤ доступных на каждом узле;
- `Σused·pue ≤ power_limit`, `Σused ≤ cooling_limit`;
- один ресурс - одному заданию (`used_mask` уникален для задачи);
- завершение/вытеснение/просрочка дедлайна освобождает ресурсы;
- результат регистрируется один раз (`status` в `DONE`/`FAILED` не меняется).

## Воспроизводимость

Начальная конфигурация узлов и заданий детерминирована при одном `-n`: `srand(seed)` вызывается в родителе до `fork()` и до `init_simulation()`.

Дальнейший ход зависит от планирования ОС (порядок фаз задан жёстко, но `rand()` внутри `node_work` пересеивается независимо в каждом воркере). Полная побайтовая воспроизводимость между запусками многопроцессной модели не гарантируется.

## Запуск

### Сборка

```sh
make             # собрать => build/sim
make rebuild     # полная пересборка
make run         # ./build/sim -t 60 -d 150 -n 42
make gen         # ./build/sim -s edf -t 80
make fail        # ./build/sim -f 0.05 -t 100
make clean       # rm -rf build/ log.log
```

### 4–5 баллов: fork-дети, неименованные семафоры в shm

```sh
./build/sim -n 1 -t 40 -d 0
./build/sim -s edf -t 80 -f 0.03 -l run.log
```

### 6 баллов: fork-дети, именованные семафоры

```sh
./build/sim -m named -n 1 -t 40 -d 0
```

### 7–8 баллов: независимые процессы через fork+exec

```sh
./build/sim cluster -n 1 -t 40 -d 0
```

Мастер напечатает в шапке:

```
Мастер PID   : 12345
SHM имя      : /sim_shm_12345
SEM префикс  : /sim_12345
```

Ручной запуск дополнительного воркера в другом терминале (это и есть «независимо запускаемые процессы»):

```sh
export SIM_SHM_NAME=/sim_shm_12345
export SIM_SEM_PREFIX=/sim_12345
export SIM_LOG_PATH=log.log
./build/sim worker node 3      # или task 7, sched 0
```

Внешняя остановка мастера:

```sh
./build/sim stop 12345         # посылает SIGTERM
```

### Ключи CLI

| Ключ | Значение                                                          | По умолчанию |
|------|-------------------------------------------------------------------|--------------|
| `-s str` | стратегия: `fcfs` / `prio` / `edf` / `sjf`                        | `prio`       |
| `-t N` | период моделирования (тиков); `0` - без лимита                    | `60`         |
| `-d ms` | задержка между тиками; `0` - без задержки                         | `150`        |
| `-n seed` | сид генератора                                                    | `42`         |
| `-l file` | файл лога (дублируется в stdout)                                  | `log.log`    |
| `-f p` | вероятность отказа узла за тик, `0..1`                            | `0.0`        |
| `-m mode` | только legacy: `shm` - неименованные в shm; `named` - именованные | `shm`        |
| `-q` | тихий режим (не печатать статус каждый тик)                       | -            |
| `-h` | справка (+ подсказка по подкомандам)                              | -            |

### Подкоманды (7–8 баллов)

| Команда | Описание |
|---------|----------|
| `cluster [опции]` | мастер + fork/exec независимых воркеров (только именованные семафоры) |
| `worker <node\|task\|sched> <idx>` | воркер; запускается мастером или вручную (env из мастера) |
| `stop <master_pid>` | послать `SIGTERM` мастеру |

Без подкоманды - legacy-версия.

## Сборка

`Makefile`:

```make
CC      = gcc
CFLAGS  = -std=c11 -Wall -Wextra -O2 -D_GNU_SOURCE -pthread
LDFLAGS = -pthread -lrt
```

`-lrt` требуется для `shm_open`/`sem_timedwait` на glibc < 2.34 (на новых - no-op). `-pthread` покрывает `sem_init`/`sem_wait` (на старых glibc).

## Проверка корректности

```sh
# Сборка без предупреждений
make rebuild 2>&1 | grep -E 'warning|error'    # ожидается пусто

# 4–5: неименованные семафоры в shm
./build/sim -n 1 -t 20 -d 0

# 6: именованные семафоры
./build/sim -m named -n 1 -t 20 -d 0

# 7–8: независимые процессы
./build/sim cluster -n 1 -t 20 -d 0

# Завершение по сигналу
timeout -s INT 3 ./build/sim cluster -t 1000 -d 10 -n 1 ; echo "exit=$?"
# Ожидается: "ПРЕРВАНО ПОЛЬЗОВАТЕЛЕМ", exit=0

# После корректного завершения named-режима - имена убраны
ls /dev/shm/sem.sim_* /dev/shm/sim_shm_*      # пусто

# Аварийные остатки после SIGKILL (kill -9 мастера) - чистятся вручную:
#   rm -f /dev/shm/sem.sim_<pid>_* /dev/shm/sim_shm_<pid>
```
