## 1. Условие задачи

В вычислительный центр поступают задания, требующие определённого числа процессорных ядер, объёма памяти, времени и электрической мощности. Центр состоит из нескольких узлов с различными характеристиками. Планировщик выбирает задания из очереди и размещает их на совместимых свободных ресурсах. Суммарное энергопотребление и тепловая нагрузка ограничены.

Требуется разработать консольное приложение на C, моделирующее работу центра в дискретном времени (тиками). В базовой версии (4–5 баллов) - многопроцессное приложение с обменом через разделяемую память POSIX и синхронизацией неименованными POSIX-семафорами в этой же памяти. В версии на 6 баллов добавляется второй механизм - именованные POSIX-семафоры. В версии на 7–8 баллов - независимо запускаемые процессы, соединяемые через POSIX shm и именованные семафоры, с возможностью ручного запуска воркеров из другого терминала.

Все три уровня живут в одном бинарнике и переключаются из CLI.

## 2. Сценарий отображения сущностей в процессы

В модели выделены все сущности, обладающие поведением; каждая такая сущность представлена отдельным процессом. Разделяемое состояние (массивы `tasks[]`, `center`, счётчики статистики, `cur_time`, `stop_flag`, параметры запуска) размещено в одном блоке `SharedState` в разделяемой памяти POSIX (`shm_open` + `mmap(MAP_SHARED)`).

| Предметная область | Процесс | Функция | Что делает                                                                                      |
|---|---|---|-------------------------------------------------------------------------------------------------|
| Модельное время (тик) | 1 × родительский | `run_clock` | двигает `cur_time`, раздаёт фазы, собирает квитанции, публикует статус, обрабатывает прерывание |
| Вычислительный узел | `MAX_NODES` (8) × воркер | `node_work` | проверяет отказ, ведёт восстановление, при отказе «роняет» размещённые на нём задания           |
| Задание | `MAX_TASKS` (20) × воркер | `task_work` | поступление в модель, проверка выполнимости, завершение по исчерпанию `time_remaining`          |
| Планировщик | 1 × воркер | `scheduler_work` | сортирует очередь по стратегии, раздаёт ресурсы, при нехватке - вытеснение                      |
| Диспетчер ресурсов | (разделяемый код) | `placement.c` | single/multi/preempt; вызывается из `scheduler_work`                                            |
| Учёт питания и охлаждения | (разделяемый код) | `resources.c` | `power_ok`, `alloc_take/give/clear`                                                             |
| Генератор конфигурации | (однократно в родителе) | `config.c` | создаёт узлы и задания до `fork`                                                                |

Итого: 30 процессов (включая родителя).

Аргумент работы - `WorkerArg { int type; int index; }`:
`type = 1` - узел, `2` - задание, `3` - планировщик; `index` - номер в соответствующем массиве.

### Как процессы устроены в разных версиях

**Legacy (4–5 и 6 баллов).** Родитель делает `fork()`, ребёнок остаётся в том же коде, вызывает `worker_process()`, который крутит цикл `sem_wait(my_sem) => sem_wait(mtx) => работа => sem_post(mtx) => sem_post(ack_sem)`. `WorkerArg` формируется в родителе, дети получают его по значению. RNG пересеивается сразу после `fork`: `srand(seed + 100000 + i)` для узлов, `+200000 + i` - для заданий, `+300000` - для планировщика.

**Cluster (7–8 баллов).** Родитель делает `fork()` + `execv("/proc/self/exe", "worker", role, idx)`: каждый воркер - отдельный запуск той же программы с подкомандой `worker`. Связь между процессами - только через `shm_open` и `sem_open` по именам, которые родитель печатает в шапке и пробрасывает через `env` (`SIM_SHM_NAME`, `SIM_SEM_PREFIX`, `SIM_LOG_PATH`). Это позволяет вручную поднять дополнительный воркер в другом терминале и внешне остановить мастера командой `./build/sim stop <pid>`.

### Синхронизация

Разделяемое состояние `tasks[]`, `center.nodes[]`, счётчики статистики, `cur_time` защищены семафором-мьютексом `sem_mtx`. Доступ к фазам - через семафоры; барьер между фазами обеспечивает `ack_sem`.

| Примитив | Назначение                                                                                          |
|---|-----------------------------------------------------------------------------------------------------|
| `sem_mtx` | защита всего разделяемого состояния (`tasks[]`, `center.nodes[]`, счётчиков статистики, `cur_time`) |
| `node_sem[MAX_NODES]` | будит процесс узла `i` к очередной фазе                                                             |
| `task_sem[MAX_TASKS]` | будит процесс задания `i` к очередной фазе                                                          |
| `sched_sem` | будит процесс планировщика                                                                          |
| `ack_sem` | квитанция «фаза выполнена»; родитель ждёт N+M+1 сигналов через `sem_timedwait` - аналог barrier     |

Реализация зависит от режима:

- `-m shm` (4–5): неименованные семафоры, `sem_init(..., pshared=1, ...)` прямо в полях `SharedState` (`sem_mtx_emb`, `node_sem_emb[]` …).
- `-m named` / `cluster` (6 / 7–8): именованные семафоры `sem_open("/sim_<pid>_<suffix>", O_CREAT | O_EXCL, 0644, value)`, `sem_close` + `sem_unlink` при cleanup. Имена уникальны для запуска (содержат PID) - параллельные запуски не сталкиваются.

Все обращения в коде модели (`sem_wait(sem_mtx)`, `sem_post(node_sem[i])`) идут через process-local макросы `sem_mtx` => `sem_mtx_p`, `node_sem` => `node_sem_p[]`. Тип `sem_t *` одинаков в обоих режимах.

### Один тик

Родитель последовательно проигрывает три фазы, между которыми ждёт квитанции от всех воркеров через `ack_sem`:

```
ФАЗА 1 (узлы):         sem_post × N  =>  ack_sem × N
ФАЗА 2 (задания):      sem_post × M  =>  ack_sem × M
ФАЗА 3 (планировщик):  sem_post × 1  =>  ack_sem × 1
ПОСТ-ФАЗА (под mtx):   дедлайны, декремент времени, накопление энергии
                       status(t) (если verbose), delay_ms(tick_delay_ms)
```

`wait_ack_or_stop` использует `sem_timedwait` с шагом 100 мс и проверяет `stop_flag` - это даёт реакцию на `Ctrl+C` в течение ~100 мс и защищает от вечного зависания, если воркер пропал (5 секунд без ack - фаза прерывается).

Внутри каждой фазы воркеры выполняются параллельно. Порядок между процессами одной фазы определяется планировщиком ОС и недетерминирован.

### Завершение

Родитель заканчивает `run_clock` по любому из условий (`stop_flag`, `-t`, `all_done()`), затем в `finish:`:

```c
stop_flag = 1;
sem_post(node_sem[i]) для всех i;
sem_post(task_sem[i]) для всех i;
sem_post(sched_sem);

for каждого потомка:  waitpid(pid, NULL, 0);

print_summary();
close(log_fd);
sems_destroy();                    /* sem_destroy или sem_close + sem_unlink */
munmap(shm, sizeof(SharedState));
shm_unlink(shm_name);              /* только в cluster; в legacy - после mmap */
```

Воркеры просыпаются, видят `stop_flag`, выходят из `worker_process` и завершаются. Удаление имён семафоров - обязанность мастера; воркер только делает `sem_close` и `munmap`.

## 3. Реализация пользовательского интерфейса

Консольный интерфейс - через системные вызовы `write()` по дескрипторам `STDOUT_FILENO` и `log_fd`. Все сообщения дублируются в `stdout` и файл протокола. В многопроцессной модели воркеры открывают лог с `O_APPEND` (без `O_TRUNC`) - дописывания атомарны для коротких строк (`< PIPE_BUF`), интерливинга в середине сообщения нет. Мастер открывает лог с `O_TRUNC` - чистит файл один раз при старте.

Формат - построчный, каждый тик начинается с метки `[t=NNN]`:

```text
[t= 3] ПОСТУПИЛО: J3 (id=2) (ядра=8 память=16ГБ мощность=180Вт ...)
[t= 3] ЗАПУЩЕНО: J3 (id=2) -> N1, N2 | режим: группа узлов
[t= 4] N1 [########............] ядра 6/16 память 12/64ГБ мощность 180/350Вт ОК
Питание: 240/1200Вт (с PUE 1.15 = 276Вт). Тепло: 240/1100Вт
Выполняются: J1(ост.3) J3(ост.6)
Ожидают: J2
```

Ключевые события: `ПОСТУПИЛО`, `ОЖИДАЕТ`, `ЗАПУЩЕНО`, `ВЫТЕСНЕНИЕ`, `ПРЕРВАНО`, `ЗАВЕРШЕНО`, `ОТКАЗ`, `ВОССТАНОВЛЕНИЕ`, `ОТКЛОНЕНО`, `ПРОСРОЧЕНО`. В конце печатается расширенная сводка: сколько выполнено, отклонено, сколько было вытеснений, перезапусков, отказов, суммарная энергия, средние времена ожидания и пребывания, построчная таблица по каждому заданию.

Вывод статуса выполняется родителем после того, как все три фазы отработали - то есть наблюдатель видит консистентное состояние (никто не пишет в `tasks[]`/`center.nodes[]` в этот момент; гарантия - через `ack_sem`-барьер).

Версия `cluster` печатает в шапку PID мастера, имя shm и префикс семафоров, а также готовые `export`-команды для ручного запуска воркера в другом терминале.

Задержка между тиками (`-d`) обеспечивает наглядность.

## 4. Варианты запуска и завершения

**Запуск** (`main.c`, диспетчер подкоманд и разбор `argv`):

**Legacy (4–5, 6 баллов):**

| Ключ | Назначение |
|---|---|
| `-s fcfs\|prio\|edf\|sjf` | стратегия планирования |
| `-d N` | задержка между тиками, мс |
| `-t N` | период наблюдения (0 - без ограничения) |
| `-n N` | зерно генератора |
| `-l файл` | файл протокола |
| `-f p` | вероятность отказа узла за тик |
| `-m shm\|named` | механизм синхронизации (по умолчанию `shm`) |
| `-q` | тихий режим |
| `-h` | справка |

**Cluster (7–8 баллов):** те же ключи (кроме `-m`, всегда именованные семафоры) плюс подкоманда и env-переменные:

| Команда / переменная | Назначение |
|---|---|
| `cluster [опции]` | мастер + `fork/exec` независимых воркеров |
| `worker <node\|task\|sched> <idx>` | воркер (запускается мастером или вручную) |
| `stop <master_pid>` | послать `SIGTERM` мастеру |
| `SIM_SHM_NAME` | имя объекта POSIX shm (`/sim_shm_<pid>`) |
| `SIM_SEM_PREFIX` | префикс именованных семафоров (`/sim_<pid>`) |
| `SIM_LOG_PATH` | путь к логу (общий для мастера и воркеров) |

**Варианты завершения:**

1. **Естественное** - все задания достигли `DONE` или `FAILED` (`all_done()` в `run_clock`).
2. **По периоду наблюдения** - `t` достиг `time_limit` (`-t`).
3. **По прерыванию** - `Ctrl+C` / `SIGTERM` родителю; обработчик `on_signal` устанавливает `stop_flag = 1`, родитель выходит из `wait_ack_or_stop`, фазы прерываются, `finish:` будит всех, `waitpid` ждёт, `print_summary` печатает итоги, семафоры и shm удаляются.
4. **По внешней команде** - `./sim stop <pid>` (cluster) посылает `SIGTERM` мастеру; сценарий совпадает с п.3.
5. **По истечении дедлайнов** - задания с просроченным сроком переводятся в `FAILED` в пост-фазе тика, очередь естественно пустеет. Для `RUNNING`-задач, просрочивших дедлайн, освобождаются ресурсы.

Во всех вариантах вызывается `print_summary()`, `log_fd` закрывается, `sem_destroy`/`sem_close` + `sem_unlink` (в `named`/`cluster`) выполняются, `munmap` снимает shm; в `cluster` - ещё и `shm_unlink`.

При аварийном `SIGKILL` мастера: в legacy `/dev/shm` остаётся чистым (имена `unlink`-аются сразу после `mmap`/`sem_open`); в `cluster` имена семафоров и shm видны до следующего запуска - при следующем старте `cluster` их нужно чистить вручную (`rm -f /dev/shm/sem.sim_<pid>_* /dev/shm/sim_shm_<pid>`) или добавить автоочистку по мёртвым PID.

```text
project/
├── Makefile
├── README.md
├── src/
│   ├── sim.h              типы, прототипы, макросы доступа к shm, WorkerArg
│   ├── main.c             глобалы, CLI, диспетчер подкоманд,
│   │                      sems_init/sems_destroy/sems_attach_named,
│   │                      run_clock, worker_process,
│   │                      cmd_legacy / cmd_cluster / cmd_worker / cmd_stop
│   ├── output.c           write()-вывод, delay_ms, on_signal
│   ├── resources.c        power_ok (с PUE и охлаждением), alloc_take/give/clear
│   ├── placement.c        try_place_single/multi, try_preempt
│   ├── events.c           node_work, task_work, scheduler_work, status, print_summary
│   └── config.c           create_node/set_center/create_tasks/init_simulation
└── build/                 артефакты сборки
```

Сборка: `make` => `build/sim`. `Makefile` использует `wildcard src/*.c`, поэтому новые `.c` попадают в сборку автоматически. `-pthread -lrt` стоит в `LDFLAGS` (`-lrt` - для `shm_open`/`sem_timedwait` на glibc < 2.34; на новых - no-op).

Ключевое в `sim.h`: `SharedState` (единый блок в shm), макросы `tasks` => `shm->tasks` и т.п., `extern sem_t *sem_mtx_p; extern sem_t *node_sem_p[MAX_NODES]; …` - process-local указатели на активные семафоры. Все модули модели работают через макросы и **не знают** о режиме синхронизации.

## 6. Результаты работы

**Тест 1.** `./build/sim -s prio -t 60` (legacy, `-m shm`).
Задания обслуживаются по приоритету; J3 (приоритет 1) вытесняет J1 (приоритет 2); в логе видны все ключевые события. Фазы узлов/заданий/планировщика видны по тому, что сообщения `ВОССТАНОВЛЕНИЕ`/`ОТКАЗ` всегда идут раньше `ЗАПУЩЕНО` в пределах одного тика.

**Тест 2.** `./build/sim -s edf -t 60`.
Задания с дедлайном запускаются раньше; задания с `deadline = 0` уходят в конец очереди; просроченные переводятся в `FAILED` в пост-фазе. `RUNNING`-задачи, не уложившиеся в срок, снимаются с освобождением ресурсов и логом `ПРОСРОЧЕНО: … (дедлайн N, остаток K тиков)`.

**Тест 3.** `./build/sim -f 0.05 -t 100`.
При вероятности 5% в логе появляются `ОТКАЗ`, `ПРЕРВАНО`, `ВОССТАНОВЛЕНИЕ`. Отказ обрабатывается в фазе узлов - до планирования того же тика, - поэтому прерванное задание успевает вернуться в очередь и быть переразмещённым в этом же тике.

**Тест 4.** `./build/sim -q -d 0`.
Программа работает без визуальных задержек, статус не печатается, итоги корректны. За 100 тиков все задания либо `DONE`, либо `FAILED`.

**Тест 5.** `Ctrl+C` во время работы (`timeout -s INT 3 …`).
Лог содержит `ПРЕРВАНО ПОЛЬЗОВАТЕЛЕМ` и полную сводку, exit code = 0. Все 30 процессов завершаются через `waitpid`, семафоры и shm уничтожаются. В `-m named` режиме после завершения `ls /dev/shm/sem.sim_*` пустой.

**Тест 6.** `-t 0` (без лимита тиков).
Программа завершается по `all_done()` - как только все задания обработаны.

**Тест 7.** `./build/sim -m named -t 20 -d 0 -n 1`.
Поведение идентично `-m shm` при том же seed; в шапке печатается `Механизм синхронизации: named (именованные POSIX-семафоры)`. Пока идёт прогон, `ls /dev/shm` показывает `sem.sim_<pid>_*`; после завершения - пусто.

**Тест 8.** `./build/sim cluster -t 20 -d 0 -n 1`.
Мастер печатает PID, имя shm, префикс семафоров и `export`-команды. В `ps` видны 30 процессов: `sim cluster`, `sim worker node 0..7`, `sim worker task 0..19`, `sim worker sched 0`. Все дочерние - **отдельные запуски** (после `execv`). По завершении - `waitpid` всех, очистка имён.

**Тест 9.** Ручной запуск воркера к работающему мастеру.
В терминале A - `./build/sim cluster -n 1 -t 100 -d 200`. В терминале B - `export SIM_SHM_NAME=… SIM_SEM_PREFIX=… SIM_LOG_PATH=…; ./build/sim worker node 3`. Воркер подключается к тому же shm/семафорам, участвует в фазах наравне с процессами мастера (в терминале A видно, что фаза узлов отрабатывает корректно).

**Тест 10.** Внешняя остановка: `./build/sim stop <pid>`.
Мастер получает `SIGTERM`, ставит `stop_flag`, будит всех, ждёт, чистит, печатает сводку. Exit code мастера = 0.

Инварианты соблюдены во всех тестах: занятые ресурсы не превышают доступные, `Σused·PUE ≤ power_limit` и `Σused ≤ cooling_limit`, при завершении/вытеснении/просрочке дедлайна ресурсы освобождаются, результат задания регистрируется один раз.

## 7. Использование ИИ

### Промты, использованные при работе

- Напиши на C структуры Task и Node: ядра, память, мощность, флаги multi/preempt/checkpoint, состояние, карта размещения.
- Напиши шаблон генерации случайных заданий и узлов.
- Напиши функцию вывода статуса узла с ASCII-полоской загрузки ядер длиной 20 символов.
- Добавь к статусу строку про питание с учётом PUE и охлаждения, блоки «Выполняются»/«Ожидают».
- Оформи лог: `[t=%3d]`, события капсом, рамка `=`.
- Напиши итоговую сводку: общая статистика + таблица по заданиям.
- Составь Makefile с `src/`, `build/`, wildcard/patsubst, `-std=c11 -Wall -Wextra -O2`.
- Спроектируй многопроцессную архитектуру: каждая сущность с поведением - отдельный процесс, родитель раздаёт фазы, воркеры синхронизируются POSIX-семафорами, общее состояние - в POSIX shm под `sem_mtx`.
- Набор примитивов: `sem_mtx`, `node_sem[]`, `task_sem[]`, `sched_sem`, `ack_sem` (барьер между фазами).
- Напиши `worker_process` и `run_clock` с тремя фазами и `ack_sem`.
- Разложи `arrivals/do_repairs/completion/schedule/check_deadlines/do_failures/advance` на `node_work/task_work/scheduler_work` + пост-фаза в часах.

### Что исправлено вручную

- **`try_place_multi`**: память - пропорционально ядрам + досылка остатка (ИИ терял остатки от целочисленного деления).
- **`status`**: защита от деления на ноль при `max_cores == 0`.
- **`name[16]`**: явный `name[len] = '\0'`.
- **EDF**: `deadline == 0` => в конец очереди (ИИ ставил в начало).
- **`cmp_jobs`**: `case EDF: { … }` - ИИ оставил объявления в `case` без блока `{}`.
- **Порядок фаз** «узлы => задания => планировщик» и пост-фаза - сознательный выбор, ИИ предлагал оставить старый порядок.
- **Многопроцессный переход**: ИИ в первом варианте оставил `pthread_mutex_t` рядом с `sem_t`, писал `cur_time` без блокировки, забыл `free(WorkerArg)`; всё это переделано.
- **Дедлайн как крайний срок завершения**: ИИ в исходной версии проверял только `WAITING`/`PREEMPTED`; добавлена проверка `RUNNING` с освобождением ресурсов (`alloc_give` + `alloc_clear`).
- **`can_ever_fit` для multi-задач**: ИИ возвращал `true` без проверки наличия multi-узлов; добавлена проверка агрегированной ёмкости `multi`-узлов - иначе задача висит в очереди до `-t`.
- **Уникальные имена shm/семафоров**: ИИ дал константный `/sim_shm_v1`; заменено на `/sim_shm_<pid>` - параллельные запуски не сталкиваются.
- **Bounds-check в `cmd_worker`**: ИИ не проверял диапазон `idx`; при `worker node 100` был бы OOB. Добавлена проверка.
- **`wait_ack_or_stop` с таймаутом**: ИИ ждал вечно; при пропавшем воркере - зависание. Добавлен `sem_timedwait` с шагом 100 мс + проверка `stop_flag` + 5-секундный guard.
- **`O_APPEND` у воркеров, `O_TRUNC` только у мастера**: иначе воркер затирал бы лог мастера при старте.

### Критическая оценка

ИИ хорошо справляется с механическими и объёмными частями: шаблоны структур, форматирование вывода, служебные функции, `Makefile`, каркас цикла фаз, рутинный переход с pthread на sem/shm. Он корректно воспроизводит паттерн «producer-consumer через семафоры + мьютекс-семафор на критическую секцию» и правильно расставляет `sem_post`/`sem_wait`.

ИИ плохо справляется с:

- **семантикой предметной области** (тонкости приоритетов, дедлайна как крайнего срока завершения, откатов при распределении ресурсов, различия «нет значения» vs «нулевое значение»);
- **тонкостями синхронизации**: первый вариант писал `cur_time` без `mtx`, в `finish:` лишний `sem_post(&ack_sem)`, `WorkerArg` не освобождался. Всё это ловится чтением кода - ИИ сам эти проблемы не видит;
- **пограничными случаями**: порядок фаз, дедлайн для `RUNNING`, bounds-check `idx`, уникальность имён shm - всё это пришлось добавлять и обосновывать вручную.

Вывод: ИИ ускоряет написание каркаса и рутины, но проектирование многопроцессной архитектуры, выбор механизма синхронизации под каждую подзадачу и проверку корректности надо делать вручную.

## 8. Дополнительные решения

- **Три уровня в одном бинаре**: `./sim` (4–5, неименованные в shm), `./sim -m named` (6, именованные), `./sim cluster` (7–8, независимые через fork+exec). Регрессий между версиями нет.
- **Единый `SharedState`** в POSIX shm - одна `mmap`-транзакция для задач, центра, статистики, параметров запуска и встроенных семафоров. Макросы `tasks`/`center`/`cur_time`/… сохраняют имена переменных во всех модулях модели - `events.c`, `placement.c`, `resources.c`, `output.c`, `config.c` не знают о переходе с потоков на процессы.
- **Разделение `sems_init`/`sems_destroy`/`sems_attach_named`** - единственное место, где различаются режимы синхронизации. Модель работает через `sem_mtx`, `node_sem`, `…` как через обычные `sem_t *` - без `#ifdef`.
- **Барьер на `ack_sem`** через `sem_timedwait` с шагом 100 мс: каждая фаза строго дожидается всех воркеров, но родитель может реагировать на `Ctrl+C` в пределах 100 мс и не висит вечно при пропавшем воркере.
- **Единый механизм карты ресурсов** (`used_mask + alloc_cores/mem/power[]`) - одинаково работает для одного узла и для группы.
- **`fork+execv("/proc/self/exe")`** для 7–8 - воркер запускается как отдельная программа, что позволяет вручную подключить его из другого терминала (env-переменные `SIM_SHM_NAME`, `SIM_SEM_PREFIX`, `SIM_LOG_PATH` пробрасываются мастером и печатаются в шапке).
- **`stop <pid>`** - корректная внешняя остановка мастера через `SIGTERM`.
- **Уникальные имена** shm и семафоров через PID - параллельные запуски не мешают друг другу.
- **Обработка `SIGINT/SIGTERM`** в мастере через `volatile sig_atomic_t stop_flag`; воркеры `SIG_IGN` - сигнал не «размазывается» по детям, а централизованно обрабатывается родителем.
- **Стратегии планирования** - один компаратор; добавление новой стратегии требует 5 строк кода.
- **Воспроизводимость начальной конфигурации** через `-n seed`: `srand(seed)` вызывается в родителе до `fork`, поэтому узлы и задания при одинаковом `-n` создаются одинаково. RNG воркеров пересеивается независимо, чтобы отказы узлов не «синхронизировались».
- **Возможное улучшение** (не реализовано): автоочистка остатков shm/семафоров по мёртвым PID при старте `cluster` (обход `/dev/shm`, `kill(pid, 0) == ESRCH` => `unlink`) и `prctl(PR_SET_PDEATHSIG, SIGKILL)` в воркерах, чтобы после `kill -9` мастера не висели заблокированными на `sem_wait`.

## 9. Выводы

Программа моделирует работу вычислительного центра как систему из 30 процессов: родитель управляет фазами и модельным временем, узлы обрабатывают отказы и восстановления, задания - поступления и завершения, планировщик - размещение и вытеснение. Взаимодействие построено на POSIX-семафорах и разделяемой памяти POSIX, с барьером через `ack_sem` на каждой фазе.

**Уровень 4–5** - процессы через `fork`, неименованные POSIX-семафоры в shm, обмен через shm. Требования на минимальную положительную оценку выполнены полностью: программа корректно моделирует, вывод информативен, наблюдатель видит ключевые события в терминах предметной области, все варианты запуска и завершения работают, семафоры и shm удаляются при любом сценарии кроме `SIGKILL`.

**Уровень 6** - добавлен второй, ранее не реализованный вариант: именованные POSIX-семафоры `sem_open`/`sem_close`/`sem_unlink`. Переключение через `-m named`; поведение модели идентично режиму `shm`, что видно по совпадающим логам при одном seed.

**Уровень 7–8** - добавлена третья, независимо запускаемая программа: подкоманда `cluster` порождает воркеров через `fork` + `execv("/proc/self/exe", "worker", …)`. Каждый воркер - самостоятельный процесс, связь с мастером исключительно через `shm_open` + `sem_open` по именам, проброшенным через env. Воркер может быть вручную запущен в другом терминале и подключён к уже работающему мастеру. Внешняя остановка - `./sim stop <pid>`. Очистка shm и семафоров выполняется мастером после `waitpid` всех потомков.

Все инварианты соблюдены во всех трёх режимах: занятые ресурсы не превышают доступные, `Σused·PUE ≤ power_limit` и `Σused ≤ cooling_limit`, при завершении/вытеснении/просрочке дедлайна ресурсы освобождаются, результат задания регистрируется один раз. Программа собирается без предупреждений с `-Wall -Wextra -pthread -lrt`, лог сохраняется в файл, все три версии сосуществуют в одном бинаре без регрессий.
