## 1. Условие задачи

В вычислительный центр поступают задания, требующие определённого
числа процессорных ядер, объёма памяти, времени и электрической
мощности. Центр состоит из нескольких узлов с различными
характеристиками. Планировщик выбирает задания из очереди и размещает
их на совместимых свободных ресурсах. Суммарное энергопотребление и
тепловая нагрузка ограничены. Требуется разработать консольное
приложение, моделирующее работу центра.

---

## 2. Сценарий отображения сущностей в процессы

| Предметная область | Сущность в коде | Поведение |
|---|---|---|
| Вычислительный узел | структура `Node` | хранит всего/занято по ядрам, памяти, мощности; имеет состояние `OK/FAILED` |
| Задание | структура `Task` | проходит состояния `WAITING → RUNNING → DONE`, при вытеснении — `PREEMPTED`, при отказе — `FAILED` |
| Вычислительный центр | `ComputingCenter` | набор узлов + лимиты `power_limit`, `cooling_limit`, `pue` |
| Планировщик | функция `schedule` | сортирует очередь по стратегии, вызывает размещение |
| Диспетчер ресурсов | `placement.c` | подбирает узел или группу узлов; при нехватке — вытеснение |
| Учёт питания | `resources.c` | проверяет лимиты сети и охлаждения перед запуском |
| Отказ оборудования | `do_failures` | случайно выводит узел из строя, задания перезапускаются |
| Модельное время | `advance` | тик = единица времени; уменьшает остаток, копит энергию |

Каждый тик обрабатываются события в фиксированном порядке:
поступления → восстановление узлов → завершения → планирование →
контроль сроков → отказы → ход времени.

---

## 3. Реализация пользовательского интерфейса

Консольный интерфейс построен на системных вызовах `write()` по
дескрипторам. Все сообщения дублируются в `stdout` и в файл протокола
`log.log`, что обеспечивает полный след работы программы.

Формат вывода — построчный, каждый тик начинается с метки `[t=NNN]`:

```text
[t= 3] ПОСТУПИЛО: J3 (id=2) (ядра=8 память=16ГБ мощность=180Вт ...)
[t= 3] ЗАПУЩЕНО: J3 (id=2) -> N1, N2 | режим: группа узлов
[t= 4] N1 [########............] ядра 6/16 память 12/64ГБ мощность 180/350Вт ОК
Питание: 240/1200Вт (с PUE 1.15 = 276Вт). Тепло: 240/1100Вт
Выполняются: J1(ост.3) J3(ост.6)
Ожидают: J2
```

Ключевые события: `ПОСТУПИЛО`, `ОЖИДАЕТ`, `ЗАПУЩЕНО`, `ВЫТЕСНЕНИЕ`,
`ПРЕРВАНО`, `ЗАВЕРШЕНО`, `ОТКАЗ`, `ВОССТАНОВЛЕНИЕ`, `ОТКЛОНЕНО`.
В конце печатается расширенная сводка: сколько выполнено, отклонено,
сколько было вытеснений, перезапусков, отказов, суммарная энергия,
средние времена ожидания и пребывания, построчная таблица по каждому
заданию.

Задержка между тиками (`-d`) обеспечивает наглядность: наблюдатель
видит, как задания поступают, размещаются, выполняются и освобождают
ресурсы.

## 4. Варианты запуска и завершения

**Запуск** (`main.c`, разбор `argv`):

| Ключ | Назначение |
|---|---|
| `-s fcfs\|prio\|edf\|sjf` | стратегия планирования |
| `-d N` | задержка между тиками, мс |
| `-t N` | период наблюдения (0 — без ограничения) |
| `-n N` | зерно генератора |
| `-l файл` | файл протокола |
| `-f p` | вероятность отказа узла за тик |
| `-q` | тихий режим (без статуса каждый тик) |
| `-h` | справка |

**Варианты завершения:**

1. **Естественное** — все задания достигли `DONE` или `FAILED`.
2. **По периоду наблюдения** — счётчик `t` достиг `time_limit`.
3. **По прерыванию** — `Ctrl+C` или `SIGTERM`; обработчик устанавливает
   флаг `stop_flag`, цикл корректно завершается, лог дописывается.
4. **По истечении дедлайнов** — задания с просроченным сроком
   отбрасываются, очередь естественно пустеет.

Во всех вариантах вызывается `print_summary()`, файл протокола
закрывается через `close()`.

## 6. Результаты работы

**Тест 1.** `./build/sim -s prio -t 60`  
Проверено: задания обслуживаются по приоритету; J3 (приоритет 1)
вытесняет J1 (приоритет 2); в логе видны все ключевые события.

**Тест 2.** `./build/sim -s edf -t 60`  
Задания с дедлайном запускаются раньше; задания с `deadline = 0`
(без срока) уходят в конец очереди; просроченные переводятся в `FAILED`.

**Тест 3.** `./build/sim -f 0.05 -t 100`  
При вероятности 5% в логе появляются `ОТКАЗ`, `ПРЕРВАНО`,
`ВОССТАНОВЛЕНИЕ`; задания с отказавших узлов перезапускаются.

**Тест 4.** `./build/sim -q -d 0`  
Программа завершается без визуальных задержек, статус не печатается,
итоги корректны.

**Тест 5.** `Ctrl+C` во время работы  
Лог содержит строку `ПРЕРВАНО ПОЛЬЗОВАТЕЛЕМ` и полную сводку.

Инварианты соблюдены во всех тестах: занятые ресурсы не превышают
доступные, питание и охлаждение не выходят за лимиты, при завершении
и вытеснении ресурсы освобождаются, результат задания регистрируется
один раз.

## 7. Использование ИИ

### Промты, использованные при работе

- Напиши на C структуры `Task` и `Node` для модели
  вычислительного центра: ядра, память, мощность, флаги
  `multi/preempt/checkpoint`, состояние, карта размещения по узлам.
- Напиши функцию вывода статуса узла с ASCII-полоской загрузки
  ядер длиной 20 символов.
- Добавь к статусу строку про питание с учётом PUE и лимита
  охлаждения, а под узлами — блоки „Выполняются“ и „Ожидают“
  с остатком времени у каждой задачи.
- Сделай красивое оформление лога: каждый тик начинается с метки
  `[t=%3d]`, ключевые события пишутся капсом (`ПОСТУПИЛО`,
  `ЗАПУЩЕНО`, `ЗАВЕРШЕНО`), блок узлов отделяется рамкой из `=`.
- Напиши итоговую сводку: блок общей статистики (выполнено,
  отклонено, вытеснений, перезапусков, энергия) плюс построчную
  таблицу по заданиям с колонками Поступл./Запуск/Финал/Состояние.
- Составь Makefile для проекта с исходниками в `src/` и объектниками
  в `build/`, с флагами `-std=c11 -Wall -Wextra -O2`.
- Напиши шаблон генерации случайных заданий и узлов.

### Что сгенерировано ИИ

- Черновые структуры `Task` и `Node` с полями — на их основе потом
  добавлены `alloc_*[]` для поддержки групп узлов.
- Функция `print_status` с ASCII-полоской — готовая визуализация.
- Шаблон Makefile с `wildcard/patsubst` и order-only предпосылкой.
- Заготовка `generate_random/create_tasks` — правила распределения
  вероятностей флагов.
- Красивый вывод статуса. Рамка из `=` по ширине сообщения тика,
  выравнивание колонок через `%-4s`, `%2d`, `%5d`, разделители
  между блоками. Сразу видно, где кончается один тик и начинается
  следующий.
- ASCII-полоска загрузки ядер. `[########............]`
  заполняется пропорционально занятым ядрам; ИИ сделал её через
  буфер из 20 символов `'#'`/`'.'` с нуль-терминатором.
- Блоки «Выполняются» и «Ожидают». Перечисление задач с
  остатком времени в формате `%s(ост.%d)`.
- Сводка по питанию с PUE. Строка
  `Питание: X/Y Вт (с PUE 1.15 = Z Вт). Тепло: X/Y Вт`.
- Хроника событий. Каждое событие — отдельная строка с меткой
  `[t=%3d]` и ключевым словом капсом. Лог читается как хроника.
- Итоговая сводка. Блок общей статистики плюс таблица по
  заданиям, выровненная через `%-8s`, `%8d`, `%6d`.

### Что исправлено вручную


1. **Распределение памяти в `try_place_multi`.** В исходном варианте
   память делилась между узлами группы поровну, при этом остаток
   от целочисленного деления не учитывался (например, при делении
   5 ГБ на 3 узла 2 ГБ оставались нераспределёнными). Изменено:
   память распределяется пропорционально числу полученных ядер,
   после чего остаток явно досылается узлам, у которых есть
   свободная память.

2. **Защита от деления на ноль в `print_status`.** Вычисление
   длины индикатора загрузки выполнялось как
   `used_cores * 20 / max_cores` без проверки знаменателя. При
   `max_cores == 0` это приводило к аварийному завершению.
   Добавлена проверка через тернарный оператор.

3. **Формирование имени задачи.** В генераторе использовалось
   выражение `rand() % 15 + 1` в буфере `char name[16]`. При
   максимальной длине строка оставалась без нуль-терминатора,
   что приводило к чтению памяти за границей массива функциями
   `printf`/`snprintf`. Длина ограничена, добавлена явная запись
   `name[len] = '\0'`.

4. **Учёт дедлайна в стратегии EDF.** Компаратор сортировал задачи
   с `deadline == 0` («без срока») перед задачами с конкретными
   сроками, что противоречит семантике поля. Ветка EDF переписана:
   задачи без срока помещаются в конец очереди.
Всё остальное — каркас программы, `Makefile`, разбор CLI, вывод
событий, сводки, модульная структура — оставил как сгенерировал ИИ,
только местами поправил комментарии.

### Критическая оценка

ИИ хорошо справляется с механическими и объёмными частями:
шаблоны структур, форматирование вывода, служебные функции,
Makefile. Плохо — с семантикой предметной области: тонкости
приоритетов, откатов в транзакциях распределения ресурсов,
различия между «нет значения» и «нулевым значением» (дедлайн).

## 8. Дополнительные решения

- Разделение на модули (`output/resources/placement/events/config`) —
  каждый модуль отвечает за один аспект модели, что упрощает
  сопровождение и тестирование.
- Ввод-вывод только через `write()/open()/close()` — даже
  форматирование выполняется через `vsnprintf` в буфер и последующий
  системный вызов.
- Единый механизм карты ресурсов (`used_mask + alloc_cores/mem/power[]`) —
  одинаково работает и для одного узла, и для группы.
- Обработка `SIGINT/SIGTERM` через флаг `sig_atomic_t` —
  гарантирует корректное завершение по прерыванию с сохранением лога.
- Стратегии планирования реализованы одним компаратором — добавление
  новой стратегии требует 5 строк кода.
- Воспроизводимость через `-n seed`.

## 9. Выводы

Программа моделирует работу вычислительного центра: принимает поток
заданий, распределяет их по узлам, учитывает энергопотребление и
охлаждение, поддерживает вытеснение с контрольными точками, отказы
узлов с восстановлением, четыре стратегии планирования. Все инварианты
соблюдены, вывод информативен, работа завершается корректно по любому
из сценариев, лог сохраняется в файл. Проект разбит на модули,
собирается без предупреждений с `-Wall -Wextra`.
